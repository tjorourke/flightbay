# What Flightbay collects, and what it never collects

Generated by `flightbay docs collects` from the collector's own tables. Do not edit by hand.

Flightbay collects only what the collection policy selects. You choose the policy before anything is read: a profile, a config file (`--config`), flags, or `collect --interactive`. Run `flightbay collect --dry-run` to see the resolved selection and the RBAC it needs; a dry run reads API discovery only. The bundle is written locally; uploading is a separate step.

## Never collected

- **Secret values.** Secrets are reduced to name, namespace, type, labels, annotations (without `last-applied-configuration`), owner references and, with `--secrets keys`, key names and byte lengths. With `--secrets metadata` the Secret body is never requested (metadata API). `--secrets omit` skips Secrets entirely.
- **Helm values.** Helm release Secrets are reduced to chart name, version, app version, status and revision.
- **`managedFields`** on any object.
- **Envoy SDS secret sections** of proxy config dumps. Certificate details for expiry checks come from `/certs`, which contains no keys.
- **Controller krt snapshots.** The agentgateway and kgateway admin snapshot spans every namespace and can hold Secret contents, so it is never read.
- **Anything from namespaces outside the selection**, including inside proxy and control-plane dumps: entries that name other namespaces are removed before the bundle is written.
- **Anything a policy exclusion covers**, through any collector. If a diagnostic endpoint would expose an excluded resource type, it is skipped and the reason recorded.

## Profiles

| Profile | Categories | Object detail | ConfigMaps | Secrets | Logs |
|---|---|---|---|---|---|
| minimal | objects, events | metadata | metadata | metadata | not collected |
| standard | objects, events, logs, helm | full | scrubbed | keys | current and previous streams, last 24h, up to 20 MiB per stream (newest kept) |
| custom | none until you choose | full | scrubbed | keys | not collected |

Cluster-scoped objects (nodes, CRDs, ClusterRoles) need `--cluster-scoped`. Proxy dumps, control-plane debug output and metrics need `--solo-diagnostics` (or the categories plus `--portforward`).

## Categories

| Category | What is read |
|---|---|
| objects | `list` of each selected resource type in the selected namespaces, in bounded chunks. CRD definitions of selected custom resources (names and printer columns; the schema is dropped). |
| events | `events.k8s.io/v1` and core events in the selected namespaces. |
| logs | `pods/log` for selected containers with `timestamps=true`, within the time window and per-stream byte limit. |
| nodes | Node objects: conditions, capacity, versions, taints (needs `--cluster-scoped`). |
| helm | Chart summaries from Helm release Secrets (needs `--secrets keys`). |
| proxies, control-plane, metrics | Admin endpoints of Solo components among the selected pods, through port-forward. See below. |

## Observed traffic (flows)

Who actually called whom comes from logs already selected above, plus optional flow logs. Nothing extra is read from the cluster unless you ask for it.

| Source | Where it comes from | Notes |
|---|---|---|
| ztunnel | ztunnel access logs (`access`, `http_access`) | Counted once per connection even when both ends log it. |
| agentgateway | agentgateway request logs (scope `request`, text or JSON) | Route, gateway, backend endpoint, `jwt.sub`, MCP method and tool, A2A method, LLM provider. 401 and 403 count as denied. |
| envoy | `istio-proxy` access logs of sidecars, Istio gateways and waypoints (Istio's default text format or its JSON encoding) | Upstream cluster gives the destination; RBAC, ext_authz, 401/403 and BlackHoleCluster count as denied. |
| coredns | CoreDNS query logs | External names only: in-cluster names, reverse lookups and search-path expansions are skipped. The CoreDNS `log` plugin is **off by default**; add `log` to the Corefile for these to exist. |
| hubble, calico, aws-vpc, gcp-vpc, azure-vnet, generic | `flightbay collect --attach-flows FILE[@CONTEXT]` | Customer-supplied flow logs embedded under `clusters/<context>/flows/<format>/<file>` and covered by the manifest. Records naming namespaces outside the selection are removed and every line is redacted before writing. |
| hubble (live) | `flightbay collect --hubble-flows[=N]` (default N = 20000) | Port-forward to the `hubble-relay` pod in `kube-system` (port 4245) and run the local `hubble observe --last N -o jsonpb`, with `--namespace` for each selected namespace. Needs port-forward, `pods` get/list and `pods/portforward` create in `kube-system`, and the `hubble` CLI on PATH; the dry run says whether it was found. Flows naming namespaces outside the selection are removed and HTTP paths redacted before writing. |

Flow files can also be added when a bundle is opened (`flightbay-desk open BUNDLE --flows FILE[@CLUSTER]`); those are marked as added by the reviewer and are not part of the signed bundle.

Supported flow log formats, detected per file: Cilium Hubble (`hubble observe -o json` or `-o jsonpb`), Calico Enterprise / Cloud flow logs (JSON), AWS VPC flow logs (default version 2 format, or a custom format with a header line), GCP VPC flow logs and firewall logs (Cloud Logging JSON export, as JSON Lines or an array), Azure NSG and VNet flow logs (JSON), and a generic CSV or JSON Lines file with any of these columns: `src_ip|source_ip|srcaddr`, `dst_ip|dest_ip|dstaddr`, `dst_port|dest_port|dstport`, `src_namespace`, `src_pod`, `dst_namespace`, `dst_pod`, `dst_host|dest_domain|fqdn`, `protocol|proto`, `method`, `path`, `action|verdict`, `count|packets`. The generic form is the way in for any other CNI or firewall (Antrea, Weave, kube-router, a firewall export or a SIEM query).

## Redaction

Runs in memory before anything is written, over object specs, ConfigMap data, environment variables, log lines and diagnostic output:

- `private-key`: PEM private keys (certificates are kept for expiry and SAN checks)
- `authorization`: Authorization: Bearer / Basic header values
- `jwt`: JSON Web Tokens
- `aws-access-key`: AWS access key IDs (AKIA..., ASIA...)
- `api-key`: sk-... and sk-ant-... style API keys
- `url-credentials`: user:password@ in URLs
- `sensitive-key`: the value of any key or variable whose name contains password, passwd, secret, token, api_key or credential
- your own patterns from `--redact-extra` (one Go regular expression per line)
- fields you name with `--drop-field PATH` or `dropFields` in a config file, removed from every object, e.g. `metadata.annotations["corp.example/*"]`

JSON held inside a string, such as the `kubectl.kubernetes.io/last-applied-configuration` annotation or a JSON file in a ConfigMap, is parsed and redacted with the same rules, so an environment variable or key inside an embedded manifest is caught too.

`redaction-report.json` in the bundle records how many replacements were made in each file, never the values. Review it with `flightbay inspect BUNDLE --redactions` before sending.

## In every bundle

- `bundle.json` (first): identity, case, contexts, capture start and the resolved collection policy.
- `collection-log.jsonl`: every call, including failures (RBAC denied, timeouts, truncation), so a missing file never looks like a missing object.
- `coverage/*.json`: per collection, what was expected and whether it completed, failed, was excluded or truncated. Attached and hubble flow files have a `flows` coverage entry each, with the detected format.
- `manifest.json`: capture end, completion state and a SHA-256 for every member. `flightbay inspect` verifies them.
- `manifest.sig` (last, with `--sign KEY`): your Ed25519 signature over the manifest, so Solo can check the bundle came from you unmodified. Solo only ever holds your public key.
- The SHA-256 of the collector binary, and with `--config` the policy file's SHA-256 and who approved it (`flightbay policy sign`).

Before sending, `flightbay review BUNDLE` lets you remove namespaces, resource types, objects, log streams, log lines and files and redact more, then exports a new signed bundle with `review-ledger.json`, a count of what you removed.

The bundle is a plain tar stream compressed with zstd. Open it with standard tools: `tar --zstd -tvf BUNDLE`. With `--encrypt-to` it is wrapped in age encryption and only the holder of the matching identity can read it.
