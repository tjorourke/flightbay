## R1. One namespace and Service scope, shared by every tab

**Problem.** Every tab scopes things in its own way, and none of them do it well:
- On Overview, the namespace chips are single-select with no "All" option. They show the top 3 namespaces, then `+N` (`am2NamespaceChips`, `web/ambient-v2.js:154-162`). The default is "the in-ambient namespace with the most Services", which can be hidden behind `+N` so that nothing looks selected.
- In Policies & routes, the scope chips (`am2PolFilters`, `web/ambient-policies.js`) only offer a way to add a namespace when none is selected. Once `agentdesktop ✕` is set, the only way to change it is to remove it first and then reopen the list. Choosing a namespace closes the list (`P.scopeOpen = false`), so selecting several means reopening it each time. When the list is open, all 27 namespaces appear inline as pills. **That is why Tom could not move off agentdesktop or multi-select.**
- Map has no scope at all. v2 passes `target = null`, so `scope = ''` and every Service in every namespace is drawn (`web/ambient-map.js:8,18`). The "All namespaces" checkbox only renders when there is a target (`:35`).
- Request path lists every workload in every namespace, including `kube-system` and `istio-system` (`RequestPathOptions`, `internal/ambient/request_path.go:108-136`).

**Tasks**
- [x] **R1.1 Build one scope control.** Create `am2ScopePicker({namespaces, selected, services?})` in `web/ambient-scope.js`. It is a single button that reads "Namespaces: bookinfo, kagent +1" (or "All namespaces"). Clicking it opens a popover with:
  - a search box,
  - "In ambient only" (on by default) and "Hide system namespaces" (on by default: `kube-system`, `istio-system`, `istio-eastwest`, `local-path-storage`),
  - one checkbox per namespace with its Service count and an ambient dot, and "Select all" / "Clear",
  - optionally, a second section that lists Services for the chosen namespaces, also with checkboxes (used by Map and Request path).

  The popover stays open while you tick boxes and closes on Escape or a click outside. Keyboard: arrows, Space and Enter.
- [x] **R1.2 One state, in the URL.** Hold the selection in `S.am2.scope = {ns: [], svc: []}`, serialise it as `ns=a,b&svc=ns/name,…` on every home tab, and persist it in `localStorage['flightbay.am2.scope']`. When you switch from Overview to Policies to Map to Request path, the scope stays the same. Add round-trip tests to `test/ambient-v2-routes.test.cjs`.
- [x] **R1.3 Default scope.** On first visit, select the namespaces in ambient that have at least one ambient policy or route. If there are none, select the in-ambient namespace with the most Services. Never default to "everything" when there are more than 10 namespaces.
- [x] **R1.4 Use it on Overview, Policies & routes, Map and Request path,** and remove the chip rows (`am2NamespaceChips`, and the Scope chips in `am2PolFilters`).
- *Acceptance:* on the live clusters, Tom can pick `bookinfo` + `kagent`, switch away from `agentdesktop` in one click, and keep that selection across all four tabs and a reload.

## R3. Policies & routes: filters, rows and contents

**Problems**
- **The filter bar holds 13 controls on one row:** search, Scope, 5 type pills, 3 show pills, and the By object / By Service toggle.
- **A group header appears above every object.** Most Services have exactly one route, so the page shows "kagent/anthropic · 1 object" followed by a single row, 20 times over.
- **Rows are tall:** a kind badge with the name in mono underneath, then a "Service **x** :80" cell, then a separate effect.
- **Waypoint Gateways are listed as policies.** The 12 kagent waypoints are infrastructure. They belong on the Map and in the Service header, not in a list of policies and routes. Tom asked for them to be removed.
- **Classification is wrong.**
  - An AgentgatewayPolicy that sets TLS is classed as Routing, because unmatched keys fall through to the default (`internal/ambient/policies.go:1063-1090`).
  - An HTTPRoute is always classed as Routing (`:710`), so a route with `timeouts` or `retry` never appears under Resilience, and Resilience shows 0 while 6 timeouts exist.
  - A DestinationRule takes the first feature it matches (`:893-946`).
  - Every object gets exactly one type.
- **Drift is meaningless.** 30 of 36 objects count as drift, because "missing on the other cluster" is counted whenever the namespace exists there (`internal/ambient/policies.go:172-214`), and specs are compared with a raw hash.
- **Managed by shows Unknown for kagent-created routes.** `ManagedBy` (`internal/ambient/service_config.go:78-114`) never reads `ownerReferences`, and `managedFields` is stripped on every collect (`internal/redact/redact.go:243`), so its first branch never fires.
- **The tab badge says 23 while the page says 36.** The badge counts only 5 kinds (`countConfigObjects`, `internal/ambient/services_overview.go:571,607-628`).
- **States are inconsistent.** In the same row pair, the AuthorizationPolicy says "Applied" and the HTTPRoute says "Accepted". PLAN §0.6 says both should read **Live** once the enforcing component accepts them.

## R6. Object page · Tests: richer cases and live results

**Problems**
- **Too few request fields.** The "+ Add case" modal (`am2CaseModal`, `web/ambient-object.js:164-171`) offers method, path, one header, expected status and "Why". The suite model already supports more (`internal/ambient/suites.go:66-110`): any number of headers, `host`, `port`, `direct`, and caller identity (`from`: namespace, service account, principal, workload), plus expected `rule`, `backend(s)`, `notRoute` and `weights`. The UI exposes none of them. A request body is not supported anywhere: `httpProfile.Body` exists, but `Send` never sets it (`internal/server/ambient_suites_run.go:426`).
- **Results only arrive at the end.** Run POSTs `api/ambient/suites/run`, the server runs every case and all 200 samples, and then sends one JSON response (`internal/server/ambient_suites.go:378-505`). Samples are counted after `wg.Wait()` (`ambient_suites_run.go:372-494`). Streaming already exists for the same curl runner: `POST api/ambient/http-mesh-test` sends ndjson one result at a time (`internal/server/http_mesh_probe.go:788-822`), read by `httpReadTestStream` (`web/http-mesh-test.js:91-110`).
- **A match case compares the wrong things.** In Tom's screenshot, `GET /health` expects "rule 1 → split" and got "200". Under PathPrefix `/` it should match rule 1. The runner returned a status but no backend, and the case was marked failed. When the expectation is a rule or backend and the backend cannot be found, the result must say "could not tell which backend answered", not ✕.
- On the AuthorizationPolicy page, the mockup's "Other policies that also decide for reviews" block is missing, and the header says "enforced by **waypoint**" rather than the waypoint's name (also "served by waypoint" on the HTTPRoute page).

**Tasks**
- [x] **R6.1 Full case editor.** Replace the modal with a side panel that has these sections:
  - **Request:** method, path, query, any number of headers (add and remove rows), host (another Service), port, body (for POST, PUT and PATCH), and "Send directly to the Pod (skip the waypoint)".
  - **From:** a picker of in-mesh sources (Service account / workload), a temporary Pod, or outside the mesh.
  - **Expect:** status, or rule, or backend, or "not this route", or weights with tolerance.
  - **Why:** free text.

  Edit and Duplicate on each row. Save writes the suite. Add `Body` to `Request` and pass it through `Send`.
- [x] **R6.2 Stream the run.** Add an ndjson mode to `api/ambient/suites/run` (`Accept: application/x-ndjson`). Use an emit callback in `runSuite` and in the `n > 1` loop of `Send`, reusing the flushing writer from `internal/server/start.go:676-690`. Events: `case-start`, `sample {case, backend, status, ms}` every N samples or every 250 ms, `case-done`, `done`. The final `done` carries the same body as today, so saving is unchanged.
- [x] **R6.3 Live UI.** While a run is going:
  - the observed weight bars and percentages grow as samples arrive, with a counter "87 / 200 requests";
  - status codes and p50/p95 update;
  - each match case row changes from pending to running to ✓ or ✕ as it finishes;
  - **Run** becomes **Stop** (AbortController and server cancellation).

  When it finishes, the tolerance verdict appears. Apply the same to the AuthorizationPolicy Tests table.
- [x] **R6.4 Fix match-case evaluation** for rule and backend expectations when no backend is found (see above), with a Go test using the `/health` case.
- [x] **R6.5 Restore the "Other policies that also decide" block** on the AuthorizationPolicy Tests tab, and show the waypoint's name in both object headers.
- *Acceptance:* Tom can add a case with two headers, a query string and a POST body from `bookinfo/productpage`, expecting backend `reviews-v2`. Run shows the bars moving within a second of pressing it, and Stop ends the run.

## R7. "Explain a request": decide what it is

**What it does today.** It builds a temporary case with `expect: {status: 200}` hard-coded and sends one real request through the suite runner (`web/ambient-object.js:210-214`). The result in Tom's screenshot, "403 · decided by unknown. Expected 200, got 403", has two causes:
- The "Expected 200" is invented by the UI.
- "unknown" appears because none of the three deciders can attribute the 403 on an HTTPRoute page (`meshDecider.Decide`, `internal/server/ambient_suites_run.go:590-650`):
  - no waypoint access-log line matches, because waypoint access logging is off or not ingested;
  - `reach.Explain` skips a DENY with `when` conditions;
  - `PredictDecision` only runs when the suite target is an AuthorizationPolicy (`ambient_suites.go:478-480`).

It also does not explain anything: it shows no matched rule, no backend and no list of the policies that were evaluated. As it stands, it is a worse copy of "+ Add case".

**Tasks**
- [x] **R7.1 Fold it into Tests as "Try a request".** Use a compact row above the cases table with the same fields as R6.1, and **Send**. The result shows what happened and why (R7.2), with **Save as a case** so you can keep it with an expectation. Remove the Explain tab.
- [x] **R7.2 Make the answer an explanation.** For one request, show:
  - the route rule that matched (from the HTTPRoute matcher, statically, with the reason other rules did not match);
  - the backend that answered, from the response;
  - every AuthorizationPolicy on the Service and waypoint, in evaluation order (CUSTOM, DENY, ALLOW), each marked matched or not matched with the condition that decided it;
  - the final verdict, and whether the waypoint log confirmed it.
  - On every object page, run `PredictDecision` over all AuthorizationPolicies that apply to the target Service, not only the page's own object.
- [x] **R7.3 Say when the waypoint log is not available.** Show "Waypoint access logging is off, so Flightbay predicted this from the policies", with a link to the Telemetry change that would turn it on. Do not show "unknown".
- [x] **R7.4 Investigate the 403.** Find out why `GET /` from the default source got 403 on kind-mesh2 when the only DENY needs `color: red` (the saved case `GET /reviews/0 · no header` gets 200). Check which cluster and source the explain run used, and whether `/` on reviews is refused by a different policy. Write down the finding before changing code.
